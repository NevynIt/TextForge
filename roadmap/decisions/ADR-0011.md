# ADR-0011 - Local AI capability architecture and semantic assistance layer

## Status

Proposed

## Date

2026-06-07

## Context

TextForge is a modular local-first React workbench for text-first authoring, structured models, and package-owned visual surfaces. The active roadmap baseline is Roadmap V20. The current validated baseline already includes the contribution/capability spine, provider-aware resources, repository/include resolution, ITM foundation, ITM static projections, Lua automation, Visual ITM runtime recovery, Cytoscape/jsMind/Sigma runtime renderers, and the read-only BPMN visual chain through `WP-BPMN-VISUAL-B`.

The existing AI roadmap entries are primarily backend-oriented or chat-oriented:

- `WP-AI-MEDIATOR` - AI contract and backend mediator;
- `WP-AI-CHAT` - AI client and chat surface;
- `WP-AI-PREF` - AI preference integration.

Those entries are still useful, but browser-local AI changes the architecture. TextForge should not treat local AI as merely a chat box or a backend-mediated feature. It should treat local AI as a policy-gated capability provider that can be used by commands, diagnostics, Markdown flows, ITM semantic review, visual surfaces, search, change proposals, and future workspace intelligence.

Chrome built-in AI currently exposes feature-detectable browser APIs for language detection, translation, summarization, prompt/general language model access, and experimental writing/proofreading assistance. Current Chrome documentation lists:

- Translator API;
- Language Detector API;
- Summarizer API;
- Prompt API / `LanguageModel`;
- Writer API;
- Rewriter API;
- Proofreader API.

The runtime status of each API varies by Chrome version, platform, origin-trial state, extension/web context, hardware, storage, language support, and model download state. Therefore TextForge must not hardcode availability. It must use runtime feature detection and `.availability()` checks before exposing actions.

Chrome built-in AI does not currently expose an embeddings API in its built-in AI API overview. Embeddings and true vector search must therefore be modelled as a separate optional local provider seam rather than assumed to be available through Chrome.

This decision extends the roadmap with a local AI capability architecture while preserving the existing local-first and suggest-only safety posture.

## Decision

Create a new roadmap module for local AI and semantic assistance:

- `MOD-LOCAL-AI` - Local AI and semantic assistance.

Create a staged set of candidate workpackages:

1. `WP-AI-LOCAL-01` - Browser local AI provider and policy-gated capability contract.
2. `WP-AI-LOCAL-COMMANDS` - Local AI command palette and editor actions.
3. `WP-AI-MD-ASSIST` - Markdown authoring, review, extraction, and report assistance.
4. `WP-AI-ITM-REVIEW` - ITM semantic review, diagnostics, and patch proposals.
5. `WP-AI-SEARCH-01` - Workspace semantic search without embeddings, using deterministic retrieval plus local AI reranking.
6. `WP-AI-EMBED-01` - Optional local embedding/vector provider contract and vector index.

The new module is local/browser-side. It does not replace `MOD-BACKEND-ENTERPRISE`, `WP-AI-MEDIATOR`, `WP-AI-CHAT`, or `WP-AI-PREF`. Instead:

- `WP-AI-MEDIATOR` remains the optional backend-mediated AI path;
- `WP-AI-CHAT` may later consume either a backend AI provider or a local AI provider depending on policy and availability;
- `WP-AI-PREF` should apply user/workspace policy across both backend and local providers;
- `MOD-LOCAL-AI` owns the browser-local provider contract, feature detection, local-only policy gates, and local semantic assistance services.

Local AI must be implemented as a capability provider behind the existing contribution/capability spine, not as direct browser API calls scattered across UI components.

## Capability model

TextForge should expose local AI as typed capabilities.

Suggested capability identifiers:

```text
localAi.detectLanguage
localAi.translateText
localAi.summarizeText
localAi.promptText
localAi.promptStructured
localAi.rewriteText
localAi.proofreadText

localAi.reviewMarkdown
localAi.reviewItm
localAi.explainDiagnostic
localAi.suggestPatch
localAi.generateChangeProposal

localAi.semanticSearch
localAi.embedText
localAi.vectorIndex
```

Initial Chrome-backed mapping:

| TextForge capability | Browser backing |
|---|---|
| `localAi.detectLanguage` | `LanguageDetector` |
| `localAi.translateText` | `Translator` |
| `localAi.summarizeText` | `Summarizer` |
| `localAi.promptText` | `LanguageModel` |
| `localAi.promptStructured` | `LanguageModel` with constrained structured output where available |
| `localAi.rewriteText` | `Rewriter`, experimental |
| `localAi.proofreadText` | `Proofreader`, experimental |
| `localAi.embedText` | not Chrome-backed initially |
| `localAi.vectorIndex` | not Chrome-backed initially |

Provider availability must distinguish at least:

```text
unsupported
available
requires-download
downloading
unavailable-by-policy
unavailable-by-device
unavailable-by-language
unavailable-by-context
error
```

This avoids misleading users when an API exists but cannot run because the model is not downloaded, the device does not meet requirements, the current browser context is unsupported, or the workspace policy disables AI.

## Provider contract

The initial provider contract should be narrow and stable.

Illustrative shape:

```ts
export interface LocalAiProvider {
  readonly id: string;
  readonly label: string;

  getCapabilities(): Promise<LocalAiCapabilityReport>;

  detectLanguage?(request: DetectLanguageRequest): Promise<DetectLanguageResult>;
  translateText?(request: TranslateTextRequest): Promise<TranslateTextResult>;
  summarizeText?(request: SummarizeTextRequest): Promise<SummarizeTextResult>;
  promptText?(request: PromptTextRequest): Promise<PromptTextResult>;
  promptStructured?<T>(request: PromptStructuredRequest): Promise<PromptStructuredResult<T>>;
  rewriteText?(request: RewriteTextRequest): Promise<RewriteTextResult>;
  proofreadText?(request: ProofreadTextRequest): Promise<ProofreadTextResult>;
}
```

Provider implementations:

```text
chromeBuiltInAiProvider
noopLocalAiProvider
futureExtensionLocalAiProvider
futureBackendMediatedAiProvider
futureLocalEmbeddingProvider
```

The `noopLocalAiProvider` is mandatory. It gives stable UI behavior when local AI is unavailable or disabled.

## Policy model

Local AI must be controlled by explicit policy.

Recommended policy modes:

```text
disabled
local-only
backend-mediated
external-provider
```

For this ADR, only `disabled` and `local-only` are in scope for `MOD-LOCAL-AI`. Backend and external provider policies remain under backend/enterprise decisions unless a later ADR consolidates all AI provider policy.

Local-only mode means:

- no TextForge-managed external AI service call;
- no hidden file scanning;
- no automatic cross-resource context collection;
- user-triggered actions only, unless a later accepted ADR defines a specific background indexing mode;
- explicit scope selection for current selection, current file, selected subtree, selected view, or selected workspace resources;
- every semantic edit is a reviewable patch or change proposal;
- no automatic patch application;
- no automatic source mutation from AI output;
- clear display of provider, availability, scope, and confidence where applicable.

Chrome may need network access for initial model download. TextForge must present this separately from TextForge network behavior: the model download is browser-managed and not a TextForge data upload. TextForge should still surface this state so users understand why a local AI feature is not immediately available.

## Runtime detection

The Chrome provider must use feature detection and availability checks.

Illustrative detection pattern:

```ts
const existence = {
  languageDetector: 'LanguageDetector' in self,
  translator: 'Translator' in self,
  summarizer: 'Summarizer' in self,
  prompt: 'LanguageModel' in self,
  writer: 'Writer' in self,
  rewriter: 'Rewriter' in self,
  proofreader: 'Proofreader' in self,
};
```

Each exposed action must also call the corresponding `availability()` method with the same options intended for the operation. UI must not enable actions solely because a global constructor exists.

For prompt calls, TextForge should prefer structured output for diagnostics, review findings, classifications, and patch proposals where supported. Structured responses must still be validated by TextForge before being trusted.

## Embeddings and vector search

This ADR explicitly separates semantic search from embeddings.

### Deterministic search remains first

The first search layer is deterministic and should be owned by existing workspace and knowledge modules:

```text
file names
resource descriptors
Markdown headings
Markdown links and backlinks
ITM ids
ITM types
ITM tags
ITM attributes
ITM relationships
diagnostics
comments
change proposals
roadmap IDs
```

This layer is mandatory and should not depend on AI.

### Semantic search without embeddings

`WP-AI-SEARCH-01` should provide semantic search without requiring vectors:

```text
user query
-> deterministic candidate retrieval
-> small candidate set
-> local AI reranking / explanation
-> cited workspace results
```

This gives practical semantic search while remaining compatible with current Chrome built-in AI.

Example uses:

```text
Where did we discuss BPMN write-back?
Find the roadmap items related to visual deltas.
Find ITM nodes that look like requirements but are not typed as requirements.
Find Markdown sections that explain backend security policy.
```

### Optional vector search

`WP-AI-EMBED-01` is a later optional workpackage. It introduces a provider contract for embeddings and a local vector index. It must not assume Chrome built-in AI provides embeddings.

Illustrative provider shape:

```ts
export interface LocalEmbeddingProvider {
  readonly id: string;
  readonly label: string;

  availability(): Promise<EmbeddingAvailability>;
  embedText(input: string, options?: EmbeddingOptions): Promise<Float32Array>;
}
```

Indexable units may include:

```text
Markdown sections
ITM nodes
ITM descriptions
ITM relationships with surrounding context
diagnostics
comments
change proposals
roadmap workpackages
ADR sections
package/module documentation
generated summaries
```

Vector storage should be local and workspace-scoped, likely using the same IndexedDB/Dexie direction already used by local workspace services. The vector index is derived data and must be rebuildable.

## Markdown assistance

`WP-AI-MD-ASSIST` applies local AI to Markdown and ITM-in-Markdown flows.

User-triggered editor actions:

```text
summarize selection
summarize section
summarize file
rewrite selection shorter
rewrite selection clearer
translate selection
detect language
extract action items
extract decisions
extract open questions
extract glossary terms
convert rough notes to structured Markdown
```

Review actions:

```text
review heading hierarchy
review report structure
find duplicated sections
find unclear terminology
find missing executive summary
find weak decision/rationale separation
find sections that should become ITM models
find Markdown blocks that should be referenced from itm-pub
```

Extraction actions:

```text
Markdown -> ITM decisions
Markdown -> ITM requirements
Markdown -> ITM risks
Markdown -> ITM workpackages
Markdown -> ITM glossary
Markdown -> ITM comments/change proposals
```

AI-generated Markdown edits must be proposed as source patches or change proposals. TextForge should show a diff and allow discard, copy, or apply through the normal edit path.

## ITM semantic review

`WP-AI-ITM-REVIEW` is the highest-value local AI use case.

ITM already has deterministic syntax, resolution, validation, selectors, rules, styles, viewpoints, views, overlays, packages, and diagnostics. Local AI must not replace deterministic validation. It should run after parsing, include resolution, type resolution, selector evaluation, and rule diagnostics.

Deterministic validators handle:

```text
indentation
syntax
malformed directives
duplicate ids
missing ids where required
unresolved links
invalid selectors
missing required attributes
invalid source/target type pairs
package/profile conformance
view/viewpoint reference errors
```

Local AI handles semantic observations such as:

```text
this node looks like a risk but is not typed as [Risk]
this requirement is vague or not testable
these two nodes look like duplicates
this label is too generic for a stable model element
this task probably needs an owner or status
this BPMN process appears to miss an end event
this gateway label should probably be a question
this relationship type may not match the source and target semantics
this ArchiMate-like element may be in the wrong layer
this subtree mixes abstraction levels
this view omits relationships needed to understand the selected nodes
```

Outputs must be normal TextForge diagnostics, observations, or review findings.

Illustrative diagnostic shape:

```json
{
  "source": "local-ai.itm-review",
  "severity": "observation",
  "message": "This node is named like a risk but has no [Risk] type or severity attribute.",
  "node": "payment_failure",
  "confidence": 0.72,
  "suggestedPatch": {
    "kind": "replace-range",
    "preview": "&payment_failure [Risk] Payment failure {severity: medium}"
  }
}
```

Suggested review commands:

```text
Review current ITM file
Review selected ITM subtree
Review current ITM view
Review ITM model against active packages
Review ITM model against BPMN profile
Review ITM model against ArchiMate profile
Review for duplicate concepts
Review for missing relationships
Review for naming consistency
Review for publication readiness
Explain selected diagnostic
Suggest patch for selected diagnostic
```

## Visual and graph assistance

Local AI may be used by visual ITM renderers, graph viewers, mind maps, BPMN previews, and the interactive ITM exploration workbench.

Possible user-triggered actions:

```text
explain this graph
summarize selected cluster
name selected cluster
find isolated nodes
find likely missing links
find duplicate nodes
suggest graph grouping
suggest a view definition for this concern
explain why this node appears in this view
explain why this node did not match the selector
```

AI must not write visual deltas directly. Presentation changes should become proposed `%view` deltas. Semantic changes should become source patch proposals.

This aligns with the transient/promotion model in `ADR-0010`: live AI outputs are transient until explicitly promoted.

## Workspace-wide assistance

Local AI can later support broader workbench activities:

```text
summarize a resource
summarize a resource neighborhood
explain a file's diagnostics
classify resources by purpose
suggest resource descriptions
detect stale generated outputs
summarize comments
group comments by theme
propose change proposals from comments
summarize roadmap dependency bottlenecks
extract ADR candidates from notes
summarize a release envelope
review validation evidence
```

These should be implemented as separate commands over explicit scopes, not as an always-on agent.

## Relationship with Lua and automation

Local AI may assist Lua automation, but it must not execute generated scripts automatically.

Allowed flows:

```text
explain this Lua script
explain this Lua error
suggest a Lua script to inspect unresolved ITM links
suggest a Lua transformation skeleton
suggest a validation helper
```

The user must review and run the script explicitly.

- implement `chromeBuiltInAiProvider`;

- detect Chrome built-in AI APIs;

Purpose:

- expose summarize, translate, language detection, rewrite, and diagnostic explanation actions;
- route commands through provider capabilities and policy checks;
- show results as transient surfaces, inline previews, or patch previews depending on action type.

Depends on:

- `WP-AI-LOCAL-01`;
- `WP-05C` - Command/action projection;

Depends on:

- `WP-AI-LOCAL-01`;
- `WP-MD-REPORT`;

### `WP-AI-ITM-REVIEW` - ITM semantic review, diagnostics, and patch proposals

Purpose:

- produce semantic observations and review diagnostics;
- support selected subtree, file, view, and package/profile review scopes;
- generate reviewable source patches;

Depends on:

- `WP-AI-LOCAL-01`;
- `WP-ITM-02`;
- `WP-ITM-03`;
- `WP-ITM-EXPLORATION-01` optionally for workbench integration;
- `WP-COMMENTS-SIDECAR` and `WP-CHANGE-PROPOSALS` optionally for review workflow integration.

### `WP-AI-SEARCH-01` - Workspace semantic search without embeddings

Purpose:

- use deterministic indexes to retrieve candidates;
- use local AI to rerank, classify, or explain candidates;
- provide cited workspace results;
- avoid requiring embeddings in the first semantic search slice.

Depends on:

- `WP-LINK-INDEX`;
- `WP-AI-LOCAL-01`;
- `WP-RES-01` / resource descriptors as needed.

### `WP-AI-EMBED-01` - Optional local embedding/vector provider contract and vector index

Purpose:

- define an embedding provider seam separate from Chrome built-in AI;
- add local vector index storage;
- index Markdown sections, ITM nodes, diagnostics, comments, and roadmap artifacts;
- support workspace-scoped reindexing and cache invalidation;
- allow future providers without changing search UI.

Depends on:

- `WP-AI-SEARCH-01`;
- `WP-SERVICES-LOCAL`;
- `WP-LINK-INDEX`.

This workpackage is optional and should not block local AI MVP adoption.

## Implementation sequence

Recommended sequence:

1. Add `MOD-LOCAL-AI` and `WP-AI-LOCAL-01` to `roadmap-state.yaml`.
2. Implement provider detection and `noopLocalAiProvider`.
3. Add settings/policy gates and visible availability state.
4. Add command palette actions for summarize, translate, language detection, and explain diagnostic.
5. Add Markdown assistance.
6. Add ITM semantic review.
7. Add workspace semantic search without embeddings.
8. Add optional embedding/vector provider only after deterministic search and reranking prove useful.

The first useful release should not wait for embeddings or vector search.

## Acceptance criteria

For `WP-AI-LOCAL-01`:

- TextForge can detect available local AI capabilities at runtime.
- TextForge can report unavailable capabilities without crashing.
- Local AI actions are hidden or disabled when policy disables them.
- The UI distinguishes unsupported, unavailable, downloading, and available states.
- Initial model download state is visible where the browser exposes it.
- No AI action runs without explicit user action.
- No source file is modified by AI without patch review.

For `WP-AI-LOCAL-COMMANDS`:

- A selected text range can be summarized where provider support exists.
- A selected text range can be language-detected where provider support exists.
- A selected text range can be translated where provider support exists.
- Diagnostic explanation can run against a selected diagnostic.
- Results are transient unless explicitly copied or applied through an edit flow.

For `WP-AI-MD-ASSIST`:

- Markdown review emits structured findings.
- Markdown rewrite creates a reviewable diff or replacement preview.
- Markdown extraction can propose ITM content without mutating source.

For `WP-AI-ITM-REVIEW`:

- ITM review runs only after deterministic parse/validation.
- AI review findings are labelled as AI observations or suggestions.
- Findings include source scope and confidence where useful.
- Suggested fixes are proposed as patches, not applied automatically.
- Profile-aware review can be scoped to active BPMN/ArchiMate/package definitions when available.

For `WP-AI-SEARCH-01`:

- Search works without embeddings.
- Deterministic candidate retrieval is visible in the design.
- AI reranking never invents files or locations outside retrieved candidates.
- Results cite local workspace resource IDs/paths and sections/nodes where possible.

For `WP-AI-EMBED-01`:

- Embedding support is provider-backed and optional.
- Vector indexes are workspace-scoped derived data.
- Index invalidation and rebuild behavior are defined.
- TextForge functions without any embedding provider.

## Consequences

### Positive

- Makes local AI a reusable capability across TextForge rather than a single chat feature.
- Preserves local-first operation and controlled source write-back.
- Gives immediate value through summarization, translation, diagnostic explanation, Markdown assistance, and ITM semantic review.
- Avoids blocking the first AI slice on embeddings.
- Creates a clean seam for future local embedding providers.
- Aligns AI work with existing roadmap governance, modules, workpackages, diagnostics, surfaces, and package boundaries.
- Supports both browser-local and backend-mediated AI futures without conflating them.

### Negative / trade-offs

- Browser AI API support is uneven across Chrome versions, contexts, devices, and languages.
- Some APIs are experimental or origin-trial/developer-trial only.
- Provider availability UX adds complexity.
- Local AI output is probabilistic and must be clearly distinguished from deterministic validation.
- Structured output still requires validation.
- Local model context limits mean large files and workspaces need chunking, scoping, and candidate retrieval.
- Optional embeddings introduce cache invalidation, storage, and rebuild concerns.

### Risks

- Users may over-trust AI findings if they appear beside deterministic diagnostics without clear labelling.
- Agents may implement AI shortcuts that bypass parser/validator contracts.
- UI may become noisy if every feature adds its own AI button.
- Vector search may be prematurely implemented before deterministic indexes are mature.
- Chrome API names, maturity, or availability rules may change.

Mitigations:

- Label AI findings separately from deterministic errors.
- Keep deterministic validation as the source of truth for conformance.
- Route all AI actions through central command/capability policy.
- Start with explicit user-triggered commands.
- Use runtime feature detection and provider abstraction.
- Treat embeddings as optional and later.
